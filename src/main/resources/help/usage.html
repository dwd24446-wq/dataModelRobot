一、这个插件做什么

把 Spring Boot（MyBatis-Plus 技术栈）项目的数据模型从代码与库里抽出来，重点回答一件事： 两张表到底怎么关联、这个结论有多可信。实际项目普遍不建外键，关系只能从业务代码推断， 而研发误解数据关系就会写出错代码 —— 所以每条关系都带证据链、冲突清单与可复现的置信度算式。

四层架构，只有第一层是重活：

① 插件（本面板）PSI 扫代码 + DatabaseTools 读 schema，规则引擎算证据与冲突，产出 JSON 事实源 + Mermaid 图
② JSON 事实源唯一事实源，可进版本库、可 diff。分数只在这里算一次，下游一律只读
③ MCP Server极薄的只读接口层，让 AI 客户端能查表、查关系、查算式（见第三节）
④ Skill编排 MCP + LLM 兜底推断规则引擎搞不定的模糊关系（见第四节）

首期只支持 MyBatis-Plus 技术栈（MyBatis-Plus + MyBatis-Plus-Join + dynamic-datasource + Lombok），不做通用 ORM。 运行环境：IntelliJ IDEA 2026.2+（build 262+，统一版含免费层）。DataGrip 与 IDEA Community 都不支持：前者缺 com.intellij.java（本插件要扫 Java 源码，这条依赖去不掉），后者缺 com.intellij.database；PyCharm / WebStorm / GoLand / CLion 两条都缺。

二、五分钟上手（全在 IDE 里）

第 1 步：配一次数据源（一次性，只需做一次）

  1. 打开 Database 工具窗口 → + → Data Source → MySQL，填连接与凭据。
  2. 在 Schemas 标签页里只勾选目标那一个库。
    这一步很关键：放任 introspect 整个服务器，插件会把服务器上所有库的表都拉进来， catalog 也会退化成数据源名。
  3. 等 introspection 转完（数据源图标不再转圈）。没转完时插件会如实提示「introspection 尚未完成」。
  4. 驱动不用管：由 IDE 的 Database Tools 提供，插件自己不 bundle 任何 JDBC 驱动。

第 2 步：扫描

两个入口，同一条实现，随便用哪个：本面板工具栏最左边的 扫描并加载（▶ 图标）， 或菜单 Tools → Scan Data Model（在 Tools 菜单最下方）。后台跑完整管线： 读 schema → 建实体索引 → 收五类证据 → 聚合关系 → 检五类冲突 → 算置信度。 跑完弹气泡通知，给出表数 / 关系数（HIGH、实线、虚线）/ 冲突数 / 需复核数 / 耗时 / 产物路径。

索引没建完时按钮是灰的（扫描要解析方法引用的泛型实参，索引期间的结果是残缺的），等 IDE 右下角的进度条走完再点。

产物落在 <项目根>/build/datamodel/：

<项目名>-datamodel.jsonJSON 事实源（MCP 与 Skill 只读它）
mermaid/<模块>.mmd按模块分的 ER 图（这类脚手架的表前缀天然是模块边界）。图头每行 表名["表名 中文注释"] 是 mermaid 的实体别名，表框里就显示中文；模块图合起来就是全库
adhoc/*.mmd双击表或业务范围生成的带字段 ER 图，含字段类型、注释与 PK/UK/FK 标记

第 3 步：扫完自动加载，不用再点重载

扫描一结束，本面板会自动刷到新产物（工具栏那个按钮的名字就叫「扫描并加载」）。 面板本身只读磁盘上的 JSON、不持有内存里的扫描结果 —— 好处是重启 IDE 仍能看、 且「JSON 是唯一事实源」这条不破；刷新是由扫描侧回过来推一把完成的。

扫描失败时（没配数据源、introspection 没跑完、解析报错）通知会说清原因， 面板则退回显示磁盘上一次的产物，不会停在一份不知道新旧的数据上。

第 4 步：浏览与跳转

  • 上面是树（模块 → 关系 → 证据 / 冲突），下面是选中项的详情：算式、惩罚系数与人话理由、schema 侧信号、消歧结论。
  • 双击任何一条证据或冲突 → 跳到写它的那行 Java（文件:行号）。同名文件命中多个时弹列表让你选，不猜。
  • 低于 0.60 的关系整行灰掉，与 Mermaid 的虚实线是同一条线；行尾的 [需复核] / [未对齐] 是标记。
  • 直接敲表名可以 speed search 过滤。

第 5 步：看关系图

工具栏 打开 Mermaid 关系图 → 选一个模块。 图由 IDE 自带的 Mermaid 插件渲染（打开即「编辑器 + 预览」双栏），本插件不 bundle mermaid.js。

双击表或业务范围打开带字段的 ER 图与非模态选择窗口。 勾选表、调整最低置信度或邻域的入边/出边方向后，预览会实时更新；选择只影响这张图，不改持久化业务范围。 业务范围最多 25 张表；单表邻域最多 25 个邻居，超出时按置信度取前 25，并在图头注明遗漏数量。

读图口径：

  • 写法是 被指向的表 ||--o{ 持有外键的表 : "外键列 置信度"，左边是「一」的一方。
  • 实线 = 置信度 ≥ 0.60（可采信）；虚线 = 低于该线，去核对一眼。虚线不是「错」，是「证据还不自洽」。
  • 基数从 schema 推：落点是主键/唯一键 → ||；落点不唯一 → }o（它压根不是一对多）； 外键列自己是主键 → 右边收成 ||（共享主键的扩展表就是 1:1）。
  • 表框里的中文注释：优先取数据库表注释，库里没写才用实体类 Javadoc 首段；两处都拿不到就只画表名。 注释会被洗一遍再上图（引号、方括号、% 这类会让整张图渲染失败的字符剔掉，超 30 字符截断）。
  • 模块图不画字段，单表邻域与业务范围图带字段。Mermaid 的 50,000 字符硬上限 （maxTextSize）不能靠文件内配置抬高。带字段图按 49,000 字符预算依次省略字段注释、 只留主键与关系字段；仍超预算则按置信度裁剪关系。降级与裁剪均在图头注明。

三、装 MCP Server（让 AI 客户端直接查事实源）

mcp-server/ 是独立的 Node 子项目（ESM、零构建），只读事实源、不连库、不重新打分： 置信度、档位、消歧结论全用插件算好的值，scoring 段把公式一并透出。暴露 4 个工具： get_tables / get_relations / explain_relation / list_conflicts。

安装与自检：

cd mcp-server && npm install && npm test

按所用 MCP 客户端的方式注册；以下是支持 mcpServers 配置的示例，路径要写绝对路径：

{
  "mcpServers": {
    "datamodelrobot": {
      "command": "node",
      "args": [
        "<项目根>/mcp-server/src/index.js",
        "--fact-source",
        "<项目根>/build/datamodel/<项目名>-datamodel.json"
      ]
    }
  }
}

事实源路径的优先级：--fact-source → 环境变量 DATAMODEL_FACT_SOURCE → 自动发现 ../build/datamodel/ 下的 *-datamodel.json（恰好一份就直接用；多份取字典序第一个并在 stderr 告警；一份都没有则报错并提示先跑 Scan Data Model）。所以上面那段 --fact-source 是可选的，只在要钉死某一份时才需要写。 重新扫描后事实源变了，重启一次 MCP server 才会读到新内容。

四、装 Skill（AI 编排 + 模糊关系兜底）

Skill 源码在 skills/explore-data-model/，与 mcp-server/ 平级、随仓库分发。 按所用 AI 客户端的 Skill 机制注册或链接该目录；客户端若支持命令触发，可用 /explore-data-model，也可直接问数据模型问题 （「这两张表怎么关联」「这列指向哪」「为什么这条关系是这个分」「哪些关系要复核」）。 若客户端把 Skill 复制到仓库外，运行查询脚本时设置 DATAMODELROBOT_ROOT 为本仓库根目录。

它做两件事：

  • A 探索/答问：优先调上面那 4 个 MCP 工具；MCP 没注册就自动回退到 scripts/query.mjs（复用 mcp-server 同一份数据层，不另立逻辑），所以不装 MCP 也能用。
  • B LLM 兜底：对规则引擎判不了的多义列（例如 user_id 同时匹配 member_user 与 system_users），读真实源码（import 的实体家族、字段 Javadoc）定案， 再由 scripts/record-inferred.mjs 写进独立的 overlay 文件。

兜底有几条硬不变量，由脚本强制而不是靠模型自觉：type 永远是 inferred、 置信度封顶 0.6（超过直接拒绝写入）、必须给 rationale 与至少一条带 文件:行号 的证据、 强制 needsReview=true。overlay 与事实源分文件，所以事实源永远干净、删文件即回滚。

五、怎么读置信度

公式：confidence = round2( min(noisyOr(证据权重), 0.99) × Π 惩罚系数 )。 证据权重：MPJ 显式 JOIN 0.95 / Lambda 等值 0.85 / 同名列键元组 0.90 / select 关联 0.75 / 只有命名约定 0.60。

HIGH ≥ 0.85可以闭眼采信
MEDIUM ≥ 0.60实线。可用，但值得扫一眼证据
LOW < 0.60虚线。去核对：多半是只有命名约定、或落点有竞争、或类型对不上

0.60 是一条线三个含义：Mermaid 的虚实线、MEDIUM 档位的下限、以及 Skill 里 LLM 兜底推断的封顶分。

置信度表达的是「证据之间是否自洽 + 这条关系是否成立」，不是「这个 JOIN 写得好不好」。 分数低不代表代码有 bug；反过来，代码真写了 JOIN 但两侧类型对不上，分数会被压下来 —— 那正是要看的地方。 最该看的一栏是「代码撑腰（CODE_BACKED）却分数最低」的关系，报告里有。

六、常见问题

现象原因与处理
通知说「需要先配置数据源」Database 工具窗口里没配数据源，或没勾任何 schema。见第二节第 1 步。
通知说「introspection 尚未完成」数据源还在读元数据，等它转完再点一次 Scan Data Model。
面板是空的 / 数据是旧的点工具栏「扫描并加载」重扫一次，扫完自动加载。按钮是灰的说明项目还在索引，等索引完再点。 另一种可能：面板只读 <项目根>/build/datamodel/（优先 <项目名>-datamodel.json， 否则取该目录下最新的 *-datamodel.json），所以写在别的目录里的产物它看不见。
双击证据跳不过去要么项目还在索引（状态栏会说「索引未就绪」），要么事实源是别的项目扫出来的 —— 跳转靠文件名在项目里反查，所以产物必须属于当前项目。
打开 .mmd 只有源码没有图渲染靠 IDE 自带的 Mermaid 插件 + JCEF。确认 Mermaid 插件没被禁用， 再看编辑器右上角的预览分栏是否被折叠。
图变成红色方框 Maximum text size in diagram exceeded Mermaid 的 maxTextSize 默认 50,000 字符，超了就把整份源码换成这张错误图。 插件产出自带护栏（预算 49,000，超了按分数砍并在图头写明），正常扫出来的图不会触发； 触发了说明文件被手改过。注意数字符不是数字节，一个汉字算 1 字符但占 3 字节。
某张表在图里没有默认不画「代码引用了、库里没有的表」（ER 图描述的是这个库）。 它们仍在事实源 JSON 里，标着 schemaAligned=false 且分数封顶在虚线区 —— 代码与库漂移本身就是信号。

七、已知边界（有意取舍，不是待办）

  • 模块图不画字段；单表邻域与业务范围图带字段，受表数量与 Mermaid 字符预算约束。
  • DBML 有意没做：它的关系语法不支持样式，表达不了置信度。
  • 插件内不自渲染图：交给 IDE 自带的 Mermaid 插件，省 5.1MB 的 mermaid.js 与 JCEF 依赖， 也因此 plugin.xml 不新增 <depends> —— 缺 Mermaid 插件只是不出图，插件照常工作。
  • 只支持 MyBatis-Plus 技术栈：JPA / jOOQ / QueryDSL / JdbcTemplate 的解析面是无底洞，先把最流行的脚手架吃透。 架构留了 Parser SPI 扩展点。
  • 关系是从代码推断的，不是数据库声明的：库里通常没有外键，所以每条结论都给证据与分数， 低分的要人看一眼，工具不替你做决定。
